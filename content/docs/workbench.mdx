title: "OpenUI workbench"
---

`anylumino.workbench.Workbench` builds notebook UIs through a chat with a local
coding agent. The chat sits on the left. The right side has four tabs: the live
UI, the [OpenUI Lang](https://github.com/thesysdev/openui) program the agent
wrote, the Python generated from that program, and the agent's callbacks.

![Workbench after one turn: the chat on the left and the generated sales explorer in the UI tab](assets/workbench/workbench-ui.png)

## Requirements

- `node` on `PATH`. The workbench runs the official OpenUI parser, bundled with
  the package, as a short Node subprocess: about twice per turn to merge and
  parse the program, and once per session for the system prompt. JupyterLab
  does not need Node otherwise, so install it if the kernel's `PATH` has none.
  Without it, a turn ends with "The workbench needs `node` on PATH to parse
  OpenUI programs."
- The `claude` (Claude Code) or `codex` (Codex CLI) executable on `PATH`,
  signed in.

The agents need no other setup. Sign in once in a terminal, with `/login` in
`claude` or with `codex login`. Each turn then passes its own system prompt,
tool limits, and component skill on the command line, and uses your account's
usage. The CLI's own default model and reasoning effort apply unless you pass
`model` or `effort`. A kernel started from a desktop app can
have a shorter `PATH` than your shell. To check what the kernel sees, run
`shutil.which("claude")` or `shutil.which("codex")` in a cell; `None` means the
turn will report that the CLI was not found.

## Start a workbench

```python
import pandas as pd
from anylumino.workbench import Workbench

sales = pd.DataFrame({"region": ["EMEA", "APAC", "AMER"], "revenue": [1.5, 2.0, 3.2]})

Workbench(agent="claude", session="sales", namespace={"sales": sales})
```

Ask for a UI in the chat, for example "Show the sales table with a region
selector and a button that totals the selected region". Each reply can change
the program, the callbacks, or both.

| Argument    | Effect                                                                                    |
| ----------- | ----------------------------------------------------------------------------------------- |
| `agent`     | `"claude"` or `"codex"`. A restored session keeps the agent it was created with.          |
| `session`   | Saves the session after every turn and restores it when a workbench uses the same name.   |
| `namespace` | Names the callbacks can read and the agent sees, with data frame shapes and column types. |
| `cwd`       | Directory the agent runs in. Defaults to the current directory.                           |
| `model`     | Model name passed to the CLI, such as `"sonnet"`. Saved with the session.                 |
| `effort`    | Reasoning effort passed to the CLI, such as `"low"` or `"high"`. Saved with the session.  |

`model` and `effort` apply only to the workbench's turns, not to your other CLI
use. Claude Code receives `--model` and `--effort` (`low`, `medium`, `high`,
`xhigh`, or `max`). Codex receives the `model` and `model_reasoning_effort`
config values (`minimal`, `low`, `medium`, `high`, or `xhigh`). A restored
session keeps its saved values unless you pass new ones, and the agent badge in
the header shows them. The workbench passes the values as given, so a name the
CLI does not know ends the turn with the CLI's error.

```python
Workbench(agent="codex", session="sales", namespace={"sales": sales}, effort="low")
```

## Tabs

| Tab         | Shows                                                               |
| ----------- | ------------------------------------------------------------------- |
| `UI`        | The widgets built by the generated code.                            |
| `OpenUI`    | The program after the reply's edits were merged into it.            |
| `UI code`   | The Python module that builds the `UI` tab. The tab runs this code. |
| `Callbacks` | The Python handlers from the agent's latest `python` block.         |

The code tabs are read only. Only chat turns change them.

![OpenUI tab with the program the agent wrote](assets/workbench/workbench-openui.png)

![UI code tab with the Python module generated from the program](assets/workbench/workbench-ui-code.png)

A turn is applied in full or not at all. The workbench merges and parses the
program, compiles the callbacks, generates the UI code, and builds the widgets.
If any step fails, all four tabs keep their previous content, and the chat shows
the error. The agent also gets the error with the next message.

## Callbacks

The program binds events with `@Callback(handler, context?)`: a button's action
runs on click, and an input's `on_change` runs when its value changes. The
agent writes the handlers as methods of one `App` subclass:

```python
from anylumino.workbench import App


class SalesApp(App):
    def setup(self):
        self.ui.table.set_rows(self.sales.to_dict("records"))

    def on_total(self, event):
        region = self.ui.region.value
        total = self.sales.loc[self.sales["region"] == region, "revenue"].sum()
        self.ui.result.text = f"{region}: {total}"
```

- `self.ui` is the generated `UI` widget, with one attribute per statement name.
  The `UI` tab shows that widget.
- `event` has `source` (the statement name), `value` (the new value, or `None`
  for a button), and `context` (the second `@Callback` argument).
- The `namespace` names reach the app as attributes, such as `self.sales`. The
  callbacks read no notebook globals, so the exported file takes its data
  explicitly.
- An optional `setup(self)` runs each time the UI is built. The agent uses it to
  fill tables and selectors from namespace data. The agent sees only the shape
  of a data frame and the name and type of each column, so its rows never leave
  the kernel.
- `self.ask_agent(message, context=None)` sends a chat message from a handler.
  `@ToAssistant(message)` in the program does the same without a handler.
- `Plot(layout?)` in the program creates an empty Plotly `FigureWidget`, which
  the callbacks fill through `self.ui.<name>`. The agent adds one per chart, so a
  request for a dashboard of several charts needs nothing from you. `Plot` is
  available when Plotly is installed, and the generated code then imports
  `plotly.graph_objects as go`.
- `Widget("name")` in the program mounts the widget stored under `name` in the
  `namespace`, such as a figure you built yourself.
- An exception in a handler shows in the chat. The other widgets keep working.
- Statement names that the `UI` widget already uses, such as `label`, `value`,
  or `layout`, stop the turn from applying, and the agent renames them.
- The callbacks share a module with the generated UI code in an export, so they
  cannot define `UI` or bind `al`, `ax`, or `go` to anything other than
  `anylumino`, `anylumino.astryx`, and `plotly.graph_objects`.
- A UI without handlers gets an empty `UIApp(App)` subclass, so it can still be
  exported.

## Agent access

Each turn runs the CLI as a subprocess, so the kernel stays responsive. Only one
turn runs at a time, and the stop control in the chat ends it. The agent can
read files in `cwd` but not change them:

- Claude runs with only the `Read`, `Grep`, `Glob`, and `Skill` tools, all
  allowed without a prompt, and `--permission-mode dontAsk`.
  `--strict-mcp-config` keeps your MCP servers out of the turn.
- Codex runs in its `read-only` sandbox. The sandbox does not cover MCP tools,
  so each turn turns off every server that `codex mcp list` reports. If a
  server cannot be turned off, the turn does not start.

## Component options

Most components end with an optional `options` object that sets more keyword
arguments of the widget, for example
`Table(rows, ["region", "revenue"], {sortable: true, density: "compact"})`. The
options come from the widget constructors, so the workbench accepts the same
names and types. An unknown option or a value of the wrong type stops the turn
from applying, and the chat shows the error.

The agent looks options up in the `openui-components` skill, which the workbench
ships in `anylumino/workbench/plugin/skills/openui-components/`: a `SKILL.md`
index and one file per component. Each file gives the component's options and
the Python constructor of its widget, such as
`ax.TextInput(label=..., value=..., placeholder=...)`, which handlers use to fill
a container. The Python positional order differs from the OpenUI one, so the
skill tells the agent to pass arguments by keyword. Claude loads the skill as a
plugin for each turn. Codex reads the same files by the path in its system
prompt. Both read a component's file only when they need it, which keeps the
system prompt small. After you change a widget's keywords or the catalog, run
`make workbench-skill` to regenerate the skill.

## Sessions

A named session is saved to `~/.anylumino/sessions/<session>.json` with the
messages, program, callbacks, working directory, and the agent's session ID. A
new `Workbench(session="<session>")` restores all four tabs and resumes the
agent's own session, so the agent still has the earlier conversation. If the
saved UI cannot be built, for example because a mounted widget is missing from
the new `namespace`, the `UI` tab shows the error and the chat stays usable.
A session keeps the agent it started with: passing another `agent` for a saved
session raises `ValueError`, since the agent's session ID only works with that
agent.

Sessions have no picker. List `~/.anylumino/sessions/` to see the saved names.

## How it works

This section is for maintainers. The modules are in `src/anylumino/workbench/`.

### One turn

```text
chat submit (ax.Chat)
  -> agents.py    run claude or codex as a subprocess, stream text and tool rows into the chat
  -> reply.py     split the reply into prose, one openui fence, and one python fence
  -> openui.py    merge the openui fence into the current program, then parse it (Node)
  -> export.py    run the callbacks without globals and find their App subclass
  -> codegen.py   turn the parsed tree into a module with a UI widget class
  -> UI(app)      create the app with the namespace, build the UI, run setup
  -> commit       set the four tabs and show the UI in the UI tab
  -> session.py   save the session file
```

Every step before the commit writes only to local variables. This is what makes
a failed turn leave all four tabs unchanged.

### Modules

| Module                | Role                                                                                                                                          |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `catalog.py`          | Defines the components the agent can use: props, child slots, action slots, and the event of each action slot. Emits the OpenUI library spec. |
| `prompt.py`           | Builds the system prompt from the catalog with the OpenUI prompt generator, and adds the callback contract and the namespace summary.         |
| `skill.py`, `plugin/` | Write and hold the `openui-components` skill, one file per component with its options and Python constructor.                                 |
| `openui.py`           | Runs `static/openui/openui_tool.bundle.mjs` under Node with JSON on stdin and stdout, for `parse`, `merge`, and `prompt`.                     |
| `reply.py`            | Splits a reply and rejects a reply with two fences of the same kind.                                                                          |
| `codegen.py`          | Emits deterministic Python, children before parents, and raises a named error for dynamic props and unsupported features.                     |
| `agents.py`           | Builds the CLI arguments, parses the Claude and Codex event streams, and stops a turn.                                                        |
| `session.py`          | Saves and loads sessions with an atomic write, and validates session names.                                                                   |
| `app.py`              | The `App` base class: namespace attributes, `setup`, handler calls with error routing, and `ask_agent`.                                       |
| `export.py`           | Runs the callbacks and the UI code for both the workbench and `load`, and writes the exported file.                                           |
| `export_dialog.py`    | The export dialog, which browses the kernel's folders rather than the browser's, since the kernel reads the files back.                       |
| `workbench.py`        | Assembles the panels and runs the turn.                                                                                                       |

The frontend parts are `ax.Chat` in `static/astryx/astryx_widget.js` and the
layout code in `static/layout/`. `scripts/openui_tool.mjs` is the source of the
OpenUI bundle; `npm run build` bundles it.

### Design decisions

- **OpenUI Lang:** it has a specification, a parser, a prompt generator, and an
  edit mode, so the workbench does not define its own format. The workbench
  merges every `openui` fence into the current program. A follow-up turn sends
  only the statements that changed, and a full program merges to itself.
- **The official parser under Node:** `@openuidev/lang-core` is TypeScript only.
  Parsing in the browser would need a rendered view, so session restore before
  display and headless tests would fail. A Python port is about 2.2k lines to
  keep in sync. `@openuidev/lang-core` and `zod` are pinned to exact versions,
  and `node --test` runs the bundle against OpenUI conformance fixtures in
  `tests/frontend/fixtures/openui/`.
- **Generated code, not an interpreter:** the `UI` tab is built by executing the
  module in the `UI code` tab, so the two cannot differ. The module also runs
  without the workbench.
- **App and UI classes:** the callbacks are an `App` subclass and the generated
  code is a `UI` widget class built as `UI(app)`. The app holds the data and the
  handlers and works without a widget; the UI is the widget, so it composes
  with other widgets. The namespace reaches the app through its constructor
  rather than as globals, so an export runs with explicit inputs. Statement
  names become `UI` attributes, which is why names of widget members are
  rejected.
- **The catalog is Python:** it sits next to the widget classes, and prop names
  match the constructor keywords. A test builds every entry, so a renamed
  keyword fails it. The catalog `VBox` and `HBox` build `ax.Stack`, not Lumino
  boxes: Lumino boxes split the height evenly between their children and clip
  tables and text.
- **Options in a skill:** the options of all components would roughly double
  the system prompt, so the prompt lists only the component signatures. Claude
  loads the skill with `--plugin-dir`. Codex has no per-run skill path, so its
  prompt gives the absolute path of the skill files.
- **Agent sessions:** the workbench creates the Claude session ID and passes it
  with `--session-id`, because `-n` cannot be resumed in print mode. Codex
  reports its thread ID in its first event. Claude gets the system prompt with
  `--append-system-prompt` on every turn; Codex gets it once with
  `-c developer_instructions=...`, which persists across `exec resume`.
- **Stop:** SIGTERM to the agent's process group, then SIGKILL after a grace
  period.

### Tests

- **pytest:**
  - Fake `claude` and `codex` executables on `PATH` replay streams captured from
    Claude Code 2.1.302 and codex-cli 0.163.0, in `tests/fixtures/agents/`.
  - Code generation has exact-source snapshot tests.
  - Callback tests fire events through `_handle_frontend_message`.
- **`node --test`:** the OpenUI bundle and the chat message mapping.
- **Browser:** `notebooks/openui_workbench_fake_agent.py` drives a full turn in
  JupyterLab without spending tokens.

## Export and load

**Export** in the workbench header writes the current UI to one Python file,
so the same UI runs without the workbench or the agent. It is available once a
UI is built.

1. Select **Export**. The dialog browses the kernel's folders, starting in the
   kernel's current directory.
2. Open the target folder, enter a name such as `sales`, and select **Export**.
   The name defaults to the session name, with `-` replaced by `_` so the file
   can be imported as a module.
   The workbench writes `sales.py`, replacing an existing file, and posts the
   `load` call for it in the chat. The file holds the `UI code` tab and then the
   `Callbacks` tab, with the imports of both at the top.
3. Run that call in a notebook cell:

```python
from anylumino.workbench import load

load("exports/sales.py", sales=sales)
```

`load` creates the `App` subclass with the keyword arguments, builds a `UI` for
it, runs `setup`, and returns the `UI` widget, so the cell shows the same UI.
The app is `ui.app`. A relative path is relative to the notebook's directory, or
to the calling script's directory outside Jupyter. In Jupyter that is the
kernel's current directory when `load` runs, the same directory the export
message makes its paths relative to. `ask_agent` and `@ToAssistant` warn and do
nothing outside a workbench.

The file reads no notebook globals, so it also works as an ordinary module:

```python
from exports.sales import UI, SalesApp

app = SalesApp(sales=sales)
ui = UI(app)
```

The app works without a UI, for example to call a handler in a test. The `UI`
is a widget, so it composes like any other: put it in a `TabPanel`, a
`SplitPanel`, or a stack next to other widgets.

## Limits

- The agent can use the components in the workbench catalog only: layout
  panels, cards, text, inputs, badges, tables, code blocks, Plotly figures, and
  mounted namespace widgets.
- Options that take Python callables, such as a button's `callbacks`, are not
  available. Option values must be literals.
- OpenUI `$state` variables, `Query`, `Mutation`, `@Each`, and `@OpenUrl`
  are not supported, and a reply that uses them is not applied. The `App` class
  holds the state and reads the data instead. For content whose size depends on
  the data, such as one card per region, the program declares an empty
  container and a handler fills its `widgets`. The system prompt teaches this.
